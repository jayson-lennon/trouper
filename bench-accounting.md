# Competitors-bench accounting: where trouper's 701 ns/msg actually goes

Sample-share accounting of the **exact competitors-bench shape** (one
producer actor hot-looping `n` tells at one sink actor, kanal
prime/start/done protocol) for **trouper** and **ractor**, captured under
`perf` with the `release-debug` + frame-pointer rig and reduced from the
committed folded stacks by `tools/fold_accounting.py`.

Every number below is a **share of that leg's own samples**; the ns/msg
column is derived (share × that leg's measured ns/msg) and approximate.
The point is the comparison under one taxonomy, not the absolute
microseconds.

## Provenance

- Date: 2026-09-24. Machine: 12-core Linux box, system otherwise quiet;
  both legs pinned to cores 0-5 (`taskset -c 0-5` wraps `perf` and the
  child).
- Build: `RUSTFLAGS="-C force-frame-pointers=yes" cargo build --profile
  release-debug --example profile_competitors` (frame pointers verified
  applied: **0% `[unknown]` frames** in either capture).
- Capture: `taskset -c 0-5 perf record -F 9999 --call-graph fp -o
  /tmp/<leg>.data -- target/release-debug/examples/profile_competitors`
  with `PROFILE_TROUPER=1 MESSAGES=5000000` / `PROFILE_RACTOR=1
  MESSAGES=10000000` (one runtime per process; ractor ran 10M messages
  for sample density since it is ~3× faster).
- Folding: `perf script -i <leg>.data | stackcollapse-perf.pl >
  bench-accounting-<leg>.folded`; SVGs regenerated by
  `flamegraph --colors=green < bench-accounting-trouper.folded` (blue
  for ractor).
- Reduction: `python3 tools/fold_accounting.py
  bench-accounting-trouper.folded bench-accounting-ractor.folded
  --trouper-ns 800 --ractor-ns 255`.

Measured in-run rates (one long run, not a criterion median):

| leg | messages | wall | rate | ns/msg |
|---|---:|---:|---:|---:|
| trouper (bounded-64, Block) | 5,000,000 | 4.001 s | 1,249,688 msg/s | 800 |
| ractor (unbounded cast) | 10,000,000 | 2.549 s | 3,923,196 msg/s | 255 |

Both are within ~12% of the README criterion medians (1,426,790 and
4,395,039 msg/s), confirming the profile rig faithfully mirrors the
bench. The ~2.9× ratio here matches the README's 3.1× (701 vs 228 ns).

## Method

The folded stacks partition **self time** (the deepest frame of each
sample). An anonymous `[libc.so.6]` leaf is attributed to the nearest
resolved ancestor (fp unwinding is clean, so "libc under
`step_service`" is real time libc spent on trouper's behalf — malloc
internals, memcpy, futex fast paths). Container/thread stubs
(`Box<dyn FnOnce>`, `thread_start`, thread_local plumbing) are
transparent. Remaining buckets follow the precedence documented in
`tools/fold_accounting.py`: harness signal plumbing, tokio
runtime/scheduling, sync primitives, allocation machinery, clock/syscall
vDSO, then trouper / ractor / kanal by name; anything unresolvable stays
`unwound-libc` and is reported, not hidden.

The harness bucket is ~0 in both legs: the prime/start/done kanal
signals account for 30 of 112k samples total — the timed window is
effectively all per-message work, including each leg's final flush/done
delivery.

Annotated hot path (dominant stack family; inclusive % per frame;

```text
  57.2%  trouper::kernel::step_service::{closure#0} [trouper]
    11.9%  <trouper::kernel::PanicIsolated<…future…> [trouper]

         9.5%  <MsgCtx>::send::<Tick> [trouper]

             2.1%  Arc<Tick>::new → malloc [alloc]
           3.9%  <MsgCtx>::send_payload [trouper]
             3.1%  CtxCore::child_trace → TraceCtx::caused [trouper]
               2.5%  CausalityId::new → clock_gettime [syscalls-clock]
    10.5%  drop_glue::<ClaimGuard> [alloc]          ← claim teardown
       9.7%  drop_glue::<Envelope> [alloc]
         6.4%  drop Option<RecordedOrigin> [alloc]
           3.1%  Arc<PayloadCell>::drop_slow [alloc]
         1.5%  drop Address → Arc<str> drop [alloc]   ← path string
     8.5%  flush_outbox [trouper]
       2.7%  route → route_inner [trouper]
       4.0%  Inbox mutex lock (parking_lot) [sync-prims]
         2.3%  lock_slow → spin [sync-prims]
       1.9%  RwLock<Vec<SchemaId>>::read [sync-prims]   ← emits gate
       1.8%  Semaphore::add_permits_locked [tokio-runtime]
    …(step_service's other <1%-each subtrees elided)
```

What one message costs (read straight off the tree and the folded
stacks):

- The whole run lives in `step_service` (57.2% inclusive on the hot
  worker); the producer's `ctx.send` loop is only 10.4% — **the tell
  intent is cheap; the flush pipeline that delivers it is ~4.5× the
  handler's cost**.
- `flush_outbox` is 45.5% inclusive: per message it routes (31.7%
  inclusive `route`, including the partition/projector probe path and a
  fresh `ActorPath` clone — 6.3% inclusive `Arc<str>` clone/drop for the
  path string), takes the destination's `Inbox` parking_lot mutex
  (8.2% inclusive; 2.3% of that spinning in `lock_slow`), and fires the
  wake `Notify` (3.1%).
- The emits-declaration gate reads the registry's
  `RwLock<Vec<SchemaId>>` on the flush path (1.9% + its guard drop 1.0%).
- Allocation is the single largest self bucket (33.6% ≈ 269 ns/msg), and
  it is trouper's own envelope churn: `Arc<PayloadCell>` and `Arc<Tick>`
  allocations at send (5.5% inside `ctx.send`), then the claim teardown
  at commit — `drop ClaimGuard → drop Envelope → drop RecordedOrigin /
  Address / Arc<str>` — is another ~10.5% inclusive of samples sitting
  in malloc/free inside libc.
- `CausalityId::new` per sent message reaches `clock_gettime` (2.3%
  self across the leg).
- Dispatch/claim machinery is *not* the problem: `claim_batch` is 0.5%
  inclusive; the sink's `Tick` handler is 0.6%.

Annotated hot path (same elisions):

```text
 40.5%  <SinkActor>>::processing_loop [ractor]        ← sink worker
  33.2%  … futures CatchUnwind/Map adapters [tokio-runtime]
    25.7%  handle_message → process_message [ractor]
       7.2%  SinkActor::handle (seen += 1) [ractor]
       (rest: mpsc Rx pop, try_admit_message, message clone)
 18.5%  <ProducerActor>>::processing_loop [ractor]    ← producer worker
    18.5%  ProducerActor::handle → cast loop [ractor]
      16.1%  ractor::rpc::cast → send_message → mpsc Tx push
             (5.1% inclusive list::Tx::push + block growth in malloc)
 24.3%  worker::park [tokio-runtime]                 ← scheduler idle
    8.5%  park → park_condvar → Condvar::wait [sync-prims]
    (plus steal_work 4.1%, maintenance 5.0%)
```

What one message costs:

- The message itself is a tokio `mpsc` unbounded push (send side,
  16.1% inclusive through `ractor::rpc::cast`) and a pop + enum match on
  the receive side (`core::ptr::read` of the `MaybeUninit` slot is 4.5%
  self across the leg). **Zero allocations per message** on the happy
  path — the leg's alloc bucket is 5.2% and it is mostly block *growth*
  (the queue amortizes new 32-slot blocks) plus the one-time
  `ActorProperties` Arc traffic.
- `ractor` self time (19.0%) is genuinely thin: `handle_message`
  dispatch, `try_admit_message`, the priority-port polling in
  `listen_in_priority`.
- The tokio-runtime bucket is large (31.1%) but it is **scheduler
  overhead, not message work**: the sink and producer live on separate
  workers and every done-adjacent wakeup round-trips through park /
  unpark / condvar waits (`park` 24.3% inclusive, condvar futex waits
  5.2%), task ref-count churn (`ref_inc/ref_dec`, `TaskIdGuard`),
  and the futures-util `CatchUnwind` adapter layers around each actor
  loop (33.2% inclusive of adapter frames — categorically tokio-glue,
  sampled inside the actor poll).
- `syscalls-clock` 9.4%: tokio's `maintenance` timer and ractor's
  supervision/priority-port machinery read the clock per park cycle.

## Where the ~3× goes

Reading strictly off the two tables:

1. **Allocation: +256 ns/msg.** ractor moves 10M pre-built messages
   through a preallocated ring with zero per-message allocation; trouper
   allocates the envelope at send (`Arc<PayloadCell>` + `Arc<Tick>` ≈
   5.5% of samples inside `ctx.send`) and tears the whole thing down at
   commit (`drop ClaimGuard → Envelope → RecordedOrigin/Address/Arc<str>`
   ≈ 10.5% inclusive). That is malloc/free pair per message plus
   refcount traffic on three `Arc`s and a heap `Arc<str>` path clone per
   route (6.3% inclusive). This is the largest single gap.
2. **Sync primitives: +130 ns/msg.** Same share (23% vs 21%) but a 3.1×
   larger denominator: trouper's inbox parking_lot mutex (with a real
   spin-slow path, 2.3% self), the registry `RwLock` read on every
   flush's emits gate (1.9% + guard drop 1.0%), the arc_swap debt-list
   lookups (1.4% self), and the wake `Notify` (2.0% self) — all *per
   message*. ractor's sync time is the same atomic work but mostly the
   tokio mpsc internals' uncontended atomics.
3. **The trouper bucket (205 ns/msg) is the framework's own machinery —
   route resolve, partition probes, declaration gating, claim/commit —
   and it is largely *not* matched by anything in ractor's 49 ns**, but
   a third of it is the path-string `Arc<str>` clone and the CausalityId
   clock read, which are allocation/clock buckets by leaf. The rest is
   genuine routing/dispatch logic ractor does not have (schema-registry
   routing vs a typed `ActorRef` handle).
4. **ractor pays elsewhere: tokio-runtime (79 vs 46 ns) and clock (24 vs
   19 ns).** Two workers parked on condvars, task ref-count churn, and
   clock reads per park cycle are the price of the unbounded-mpsc +
   separate-task shape. trouper's single actor-loop task per actor and
   Notify-based wake avoids most of that — its tokio bucket is tiny.
5. **Dispatch is not the gap.** Claim-batch machinery (0.5% inclusive)
   and the sink handler (0.6%) are noise in trouper; ractor's handler
   path is similarly thin (7.2% of a 255 ns leg). The difference is
   entirely in what happens *around* the handler: envelope
   materialization, routed delivery, and commit teardown.

Net: trouper spends ~270 ns/msg in allocation machinery and ~184 ns/msg
in lock/atomic work that ractor simply does not do per message, and its
routing layer (~205 ns) rides on top. The optimization directions those
numbers point at — envelope pooling / inline small-payload storage, a
path-string cache or endpoint-owned path to stop per-send `Arc<str>`
clones, and keeping the emits gate on the cell-local mirror all the way
through flush — are each grounded in a specific bucket above.

## Reproduction

```text
# build (frame pointers are the mechanism; the profile only adds symbols)
RUSTFLAGS="-C force-frame-pointers=yes" \
  cargo build --profile release-debug --example profile_competitors

# capture (one runtime per process)
PROFILE_TROUPER=1 MESSAGES=5000000 taskset -c 0-5 perf record -F 9999 \
  --call-graph fp -o /tmp/comp-trouper.data \
  -- target/release-debug/examples/profile_competitors
PROFILE_RACTOR=1  MESSAGES=10000000 taskset -c 0-5 perf record -F 9999 \
  --call-graph fp -o /tmp/comp-ractor.data \
  -- target/release-debug/examples/profile_competitors

# fold + render
perf script -i /tmp/comp-trouper.data | stackcollapse-perf.pl \
  > bench-accounting-trouper.folded
perf script -i /tmp/comp-ractor.data | stackcollapse-perf.pl \
  > bench-accounting-ractor.folded
flamegraph --colors=green < bench-accounting-trouper.folded \
  > flame_competitors_trouper.svg
flamegraph --colors=blue  < bench-accounting-ractor.folded \
  > flame_competitors_ractor.svg

# accounting (tables + trees + comparison)
python3 tools/fold_accounting.py bench-accounting-trouper.folded \
  bench-accounting-ractor.folded --trouper-ns 800 --ractor-ns 255
```

The committed folded stacks are the raw evidence; the script's output is
deterministic (verified by running it twice and diffing).

## Unique-payload round (2026-09-24)

This round combines the unique/shared payload representation, route clone
removals, and the lazy memo side box. The figures below are a before/after
measurement of the combined change; they do not isolate the individual
contribution of each refactor.

### Measurement

| method | trouper bounded-64 | ractor unbounded |
|---|---:|---:|
| Criterion, 50,000 messages (median) | 589.7 ns/msg (29.483 ms) | 225.4 ns/msg (11.270 ms) |
| Profile rig, single run | 634 ns/msg (5M in 3.172 s) | 252 ns/msg (10M in 2.517 s) |
| Prior reference | 701 ns/msg | 228 ns/msg |

The 589.7 ns/msg trouper median is approximately 15.9% below the 701 ns/msg
prior reference. Criterion reports a 16.9% improvement against its own saved
baseline (which is distinct from the rounded reference above); ractor is
within the reported noise band (−1.4%). The single-run profile improves
from the prior 800 ns/msg capture to 634 ns/msg. The independently sampled
profile run and Criterion median differ, so use Criterion for the benchmark
comparison and the profile only to attribute the combined change.

### Re-profiled bucket comparison

Same taxonomy and committed `fold_accounting.py`; the before columns are
reduced from the previous committed folded stacks at their recorded 800 / 255
ns/msg. New columns use the fresh capture at 634 / 252 ns/msg.

| bucket | prior trouper self % (ns) | unique-payload trouper self % (ns) | Δ ns/msg |
|---|---:|---:|---:|
| trouper | 25.6% (205) | 25.6% (162) | −43 |
| tokio-runtime | 5.7% (46) | 5.1% (32) | −14 |
| sync-prims | 23.0% (184) | 28.5% (181) | −3 |
| alloc | 33.6% (269) | 25.8% (163) | **−106** |
| syscalls-clock | 2.3% (19) | 2.3% (15) | −4 |
| unwound-libc | 9.7% (78) | 12.7% (81) | +3 |

The allocation bucket falls by 7.8 percentage points and approximately
106 ns/msg at the profile's measured rate. The new hot path allocates a
`Box<PayloadCell>` for the unique cell instead of `Arc<PayloadCell>`; the
profile still sees that allocation and deallocation. The baseline's sampled
teardown included `Arc<PayloadCell>::drop_slow` (3.1% of samples) and
`Arc<str>` drop (1.4%). In the new capture teardown shows the unique Box
free (3.6%), and the route no longer constructs an owned destination before
matching a plain path. These stacks support the combined decrease but do not
separately quantify the effects of representation, path-clone removal, and
memo slimming.

Ractor's profile bucket table is effectively stable: 5.2% / 13 ns/msg
allocation before, 5.1% / 13 ns/msg after; 255 → 252 ns/msg in the two
profile runs. Unwound libc is 12.7% (trouper) and 15.0% (ractor) in this
capture, so leaf-level attribution is indicative, not exact allocator-call
accounting.
